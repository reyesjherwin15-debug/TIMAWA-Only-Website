# TIMAWA — installable app + activity notifications

The site is now a Progressive Web App: members can install it to their home
screen and it opens full screen, like a normal app. Once they turn notifications
on, the squad's activities arrive as system notifications — even when TIMAWA is
completely closed and the phone is locked.

---

## 1. What was added

| File | What it does |
| --- | --- |
| `manifest.json` | App name, icons, colours, start page, shortcuts. Makes the site installable. |
| `sw.js` | Service worker: caches the app shell, serves pages offline, **receives and displays push notifications**, opens the right page on tap. |
| `pwa.js` | Shared runtime: registers the worker, shows the install banner, subscribes the device, saves the subscription to Firestore. |
| `pwa.css` | Styles for the install banner and the notification card. |
| `push-config.js` | Public VAPID key (safe to publish). Generated by `tools/generate_vapid_keys.py`. |
| `offline.html` | Shown when a member opens a page they have never visited while offline. |
| `icons/` | App icons generated from `images/Logo.jpeg` (192, 512, maskable, Apple touch, favicon, notification badge). |
| `tools/` | Sender-side Python scripts: `send_activity_push.py` (activities), `push_dispatcher.py` (live chat/announcement push). **Never upload this folder's secrets.** |
| `firestore.rules` | New `pushSubscriptions` + `pushLog` rules. |

Every page got the manifest link, iOS meta tags and the two runtime scripts in
its `<head>` / before `</body>`.

---

## 2. Publish it over HTTPS

Service workers (and therefore push) only work on **HTTPS** — or `localhost`
while testing. Firebase Hosting, Netlify, Vercel, GitHub Pages, Cloudflare Pages
all qualify out of the box.

If the site is opened as a local file (`file:///.../index.html`) the worker is
deliberately skipped and nothing breaks — notifications just stay unavailable.

---

## 3. Deploy the Firestore rules (recommended)

Open `firestore.rules` in the Firebase console → Firestore Database → Rules and
paste the whole file, then Publish.

Why: the existing blanket rule lets any signed-in member read every collection.
The new rules keep each device's push endpoint private to its owner and reserve
`pushLog` for the sender. The sender uses the Admin SDK, which bypasses rules.

> If you skip this step the feature still works — but members could read each
> other's push endpoints.

## 4. Install it on a phone

**Android / Chrome / Edge:** open the site → the *Install TIMAWA* banner appears
(or menu → *Install app*). The app then opens from the home screen, full screen.

**iPhone / iPad (Safari):** Share → **Add to Home Screen**.

* Web push on iOS exists **only inside that installed app**, iOS 16.4 or newer. A
  Safari tab has no notification API at all, so the profile card says *Available
  in the installed app* with a **How to install** button instead of a dead switch.
* Install it from **Safari** — that is the combination Apple supports for web push.
* On iPadOS the Share button is at the top of the screen; the steps are the same.
* Open TIMAWA from the new icon, sign in, then Profile → Activity notifications.

The banner's X hides it **for the current visit only** — reloading brings it back.
It stops for good once the app is installed.

---

## 5. Turn notifications on (member side)

Profile → **Activity notifications** → **Enable notifications** → allow.

* The device receives a push endpoint, which is saved to
  `pushSubscriptions/<sha256(endpoint)>` with `uid`, endpoint, keys and device
  info. One row per device; re-subscribing updates the same row.
* Turning it off unsubscribes the device and deletes its row.
* The card explains the state either way: *On*, *Off*, *Blocked by the browser*,
  *Sign in first*, or *Setup needed* (VAPID key missing). On iPhone/iPad in a
  Safari tab it says *Available in the installed app*; if notifications were
  turned off in iOS Settings it says *Turned off in iOS Settings* and points to
  **Settings → Notifications → TIMAWA**.

## 6. Send notifications (admin side)

### One-time setup

```bash
# from the project folder
python -m venv tools/.venv
tools/.venv/Scripts/python.exe -m pip install -r tools/requirements.txt
```

Get a service account key: Firebase console → Project settings → **Service
accounts** → *Generate new private key*, save it as
`tools/service-account.json` (already git-ignored).

VAPID keys already exist:

* private: `tools/.vapid-private.pem` (sender only — never upload or share)
* public: inside `push-config.js` (shipped to browsers)

Regenerate both with `tools/.venv/Scripts/python.exe tools/generate_vapid_keys.py --force`
— every member then has to enable notifications again.

### Commands

```bash
# who is subscribed?
tools/.venv/Scripts/python.exe tools/send_activity_push.py --list

# send yourself a test (do this first)
tools/.venv/Scripts/python.exe tools/send_activity_push.py --test

# announce one activity
tools/.venv/Scripts/python.exe tools/send_activity_push.py --event <eventId>

# remind everyone about everything starting in the next 24h
tools/.venv/Scripts/python.exe tools/send_activity_push.py --upcoming 24

# free-form announcement
tools/.venv/Scripts/python.exe tools/send_activity_push.py \
  --title "Gala moved" --body "Now 8 PM at the usual place"

# preview without sending
tools/.venv/Scripts/python.exe tools/send_activity_push.py --upcoming 24 --dry-run
```

The sender's VAPID `sub` claim defaults to the deployed site's origin. That works
for Chrome **and is required for Apple**: its push service rejects a `mailto:`
domain that does not exist (`403 BadJwtToken`, e.g. `…@example.com`). To identify
yourself with an inbox instead (not a secret — no password is involved):

```bash
setx VAPID_SUBJECT "mailto:you@gmail.com"
```

`--vapid-subject` overrides it per run. Use an address you actually read. A URL
with a path (`https://site.example/app/`) is reduced to its origin automatically —
the signing library rejects `sub` values that carry a path.

A notification looks like:

> **New activity: Barkada Beach Day**
> Outing • Mon, 2 Nov · 5:00 PM • Bolinao
> Meet at the usual spot, bring sunscreen…

Tapping it opens `calendar.html` in the installed app, or focuses the app if it
is already open.

### Automatic reminders

A static site has no server, so *something* has to run the sender. Easiest is
Windows Task Scheduler, once an hour:

```bat
schtasks /create /tn "TIMAWA activity reminders" /sc hourly /mo 1 /tr ^
"\"C:\Users\Jhemuel Reyes\OneDrive\Documents\TIMAWA\update\tools\.venv\Scripts\python.exe\" \"C:\Users\Jhemuel Reyes\OneDrive\Documents\TIMAWA\update\tools\send_activity_push.py\" --upcoming 24"
```

`--upcoming` is idempotent: it writes `pushLog/<eventId>__reminder` after sending,
so an event is never announced twice.

Announcements for a brand-new event are a single command (`--event <id>`). If you
want that to happen automatically the moment someone creates an event, the next
step up is a small Firebase Cloud Function with the same payload — say the word
and it can be added.

## 7. What gets pushed & how the threading works

Every engagement announcement carries the same three fields:

| field | meaning |
| --- | --- |
| `pushPending: true` | "this one is worth a system notification" |
| `pushUrl` | where a tap lands (falls back to `link`) |
| `pushContext` | the conversation this belongs to — also the notification tag |

Covered today:

| event | `pushContext` | who receives it |
| --- | --- | --- |
| Direct message | `chat:<senderUid>` | the receiver |
| @mention — chat, squad call, note, note reply, highlight comment, story caption | `mention` | each mentioned member |
| Reaction to a highlight | `reaction_<referenceId>` | the highlight's owner |
| Reaction to a story | `reaction_story_<storyId>` | the story's owner |
| Reply to a story | `chat:<senderUid>` | the story's owner |
| New highlight / uploaded post | `highlight` | everyone |
| New story posted | `story` | everyone (the author is skipped) |
| Admin announcement | `ann:<type>` | everyone, or the picked member |

`tools/push_dispatcher.py` watches those flags:

1. **every flagged event** → a notification, read or unread
2. **consecutive events in one conversation thread** — the tag comes from
   `pushContext`, so the device replaces the previous notification instead of
   stacking one per message (DMs also show "· N new" via `pushCount`)
3. **`readBy` is not a gate** — reaching the screen still closes the
   notification, but it never suppresses the next one

Run it and leave it up for live delivery:

```bash
tools/.venv/Scripts/python.exe tools/push_dispatcher.py
tools/.venv/Scripts/python.exe tools/push_dispatcher.py --once     # one pass
tools/.venv/Scripts/python.exe tools/push_dispatcher.py --dry-run  # show only
```

Any announcement can carry the same three fields, so mentions, birthdays and
feature announcements ride the same dispatcher with no extra code.

### Notification ↔ screen binding

Every notification carries a `context`, so reaching the screen it came from
resolves it **whether or not the member tapped the notification**:

| context | resolved by |
| --- | --- |
| `chat:<uid>`, `chat:group` | opening that conversation |
| `event:<id>`, `event:` | opening the calendar |
| `ann:<type>` | opening the bell |

"Resolved" closes the OS notification *and* marks the matching in-app
announcement read. Tapping a chat notification deep-links straight into the
conversation (`dashboard.html#chat_<uid>`), which resolves it the same way.

## 7b. How notifications look

The dispatcher resolves who an alert is about and attaches the right artwork:

| Alert | Artwork |
| --- | --- |
| Mention, reaction, DM, birthday | The member's **current profile photo** (`actorUid` → `users/{uid}.photoURL`) |
| Highlight, story, event, new member, admin post, note, reply | Dedicated badge from `icons/notif-*.png` |

The same faces/badges appear in the in-app notification centre on every page, so
a member sees one consistent design whether the card is on the lock screen or in
the bell menu. Sender fields are written on the announcement:

```js
actorUid: 'uid', actorName: 'Maya', actorPhoto: 'https://res.cloudinary.com/...'
```

Older queued announcements without those fields still work: the dispatcher reads
`users/{uid}` when it can, and falls back to the category badge instead of a
broken image. On iPhone/iPad, WebKit always displays the app icon on the lock
screen; the profile photo is shown inside the in-app notification list.

## 8. How it behaves

* **Offline:** pages a member has already opened are served from cache; anything
  else falls back to `offline.html`. Firestore keeps working from its own cache.
* **Updates:** `sw.js` caches under `timawa-shell-v1.5.17`. After editing any
  cached file, bump `CACHE_VERSION` so phones pick up the new shell.
* **Not cached:** Firebase, Cloudinary and CDN requests — those always go to the
  network, so data stays live and the cache stays small.
* **Battery/data:** the shell is ~150 KB; pages are cached on first visit rather
  than all at install.

### iOS specifics

* Push exists only in the home-screen app (iOS 16.4+). In a Safari tab the card
  offers the install steps rather than a permission switch.
* WebKit renders only the title, body, tag and data. Android's action buttons,
  image, badge and vibration are skipped on Apple devices by `sw.js`.
* Safari does not reliably fire `pushsubscriptionchange`, so the app re-saves its
  subscription on every launch and when it returns from the background. Endpoints
  Apple reports as gone are pruned by the sender.
* Nothing asks for notification permission on its own: the member taps **Enable
  notifications** inside Profile, which satisfies iOS's user-gesture requirement.
* iOS can evict the service-worker cache after long periods without opening the
  app; pages re-cache as they are visited.

1. Desktop Chrome → DevTools → Application → **Manifest**: name, icons, start URL.
2. **Service Workers**: `sw.js` is *activated and running*.
3. **Cache Storage**: `timawa-shell-v1.0.3` and `timawa-runtime-v1.0.3` exist.
4. Sign in → Profile → Activity notifications → Enable → row appears in
   `pushSubscriptions` in the Firebase console.
5. `--test` from the terminal → notification appears with the site closed.
6. `--event <id>` → notification shows the activity title, date and place.
7. Tap it → app opens on the calendar.
8. Airplane mode → reopen the app → last pages still load, `offline.html` for
   uncached ones.
9. **iPhone (16.4+), Safari tab** → Profile: the card reads *Available in the
   installed app* and **How to install** shows the Share steps.
10. Add to Home Screen → open from the icon → card reads *Off* → Enable → allow →
    a row appears in `pushSubscriptions`. `--test` arrives with the app closed;
    tapping it opens the calendar.
11. iOS **Settings → Notifications → TIMAWA** → turn off → reopen the app: the
    card reads *Turned off in iOS Settings*.

## 10. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Card says *Setup needed* | `push-config.js` has no VAPID public key. Run the key generator. |
| Card says *Blocked by the browser* | Site settings → Notifications → Allow, then reload. |
| No banner on desktop | Chrome only fires the install prompt on HTTPS, and not if already installed. |
| iPhone has no notifications | Must be added to the home screen first, iOS 16.4+; install it from Safari. |
| iPhone card says *Available in the installed app* | Correct behaviour — iOS has no push in a Safari tab. Tap **How to install**. |
| iPhone card says *Not supported* | iOS is older than 16.4, or the page is open outside the installed app. |
| Apple returns `403 BadJwtToken` | The VAPID `sub` points at a fictional domain. Set `VAPID_SUBJECT` to a real inbox or your site URL. |
| Sender says *Missing VAPID private key* | `tools/.vapid-private.pem` was not copied. Regenerate keys. |
| Sender says *Could not load credentials* | `tools/service-account.json` missing or not valid JSON. |
| `--test` sends 0 | Nobody has enabled notifications; check `pushSubscriptions` is not empty. |
| Rows disappear after a while | Normal: endpoints the push service reports as gone (404/410) are removed. |
| Notification arrives but tapping does nothing | Service worker was unregistered/reinstalled; reopen the app once so it re-registers. |

## 11. Security notes

* The **public** VAPID key is fine in client code; the **private** key and the
  service account key must never be uploaded. `.gitignore` covers both, but
  OneDrive still syncs them — treat that folder as private.
* Members can only read/write their own subscription rows (with the new rules).
* Push payloads contain the activity title, date, place and a trimmed
  description. No emails, no birthday dates, no private profile fields. Person
  alerts also carry the sender's display name and public Cloudinary photo URL so
  the notification can show their face.
* If a private key leaks: `python tools/generate_vapid_keys.py --force`, redeploy
  `push-config.js`, and members re-enable notifications.

## 12. Shipping an update (the "new version" prompt)

The app reads a tiny file, `app-version.json`, on every launch and compares it
with the build the device last applied (stored as `timawa.app.version`). They
only differ when you release something, so an up-to-date app never shows a card.

```json
{
  "version": "1.6.0",
  "requiresReinstall": true,
  "announceOnFirstRun": true,
  "title": "TIMAWA has a new look"
}
```

| Field | Meaning |
|---|---|
| `version` | The live build. **Bump it on every release** you want members to see the prompt for. |
| `requiresReinstall` | `true` when the icon, the manifest or the launch screen changed — the phone only re-reads those when the installed app is updated. Also tells iPhone members to remove and re-add the app. |
| `announceOnFirstRun` | `true` also prompts devices that never stored a version (members who installed before this feature existed). Set it back to `false` after that rollout. |
| `title` | Heading on the card. `message` may be added to replace the built-in wording. |

**What the member sees**

* **Update now** — records the build, asks the waiting service worker to take
  over, and reloads. Caches are *not* cleared, so a reload with no connection
  still opens the offline copy.
* **Later** — snoozed for 14 days; the card returns after that until the update
  is applied.
* On an **iPhone**, the button is **Got it** instead, with the steps to remove
  the app and add it to the Home Screen again — iOS cannot refresh an installed
  icon any other way.

The card is skipped (and shown on a later launch) when another dialog is
already up, and it never appears offline.

**Testing it**: open the console on any page and run
`TIMAWA_PWA.checkAppUpdate({ force: true })` after setting
`localStorage.setItem('timawa.app.version', '0.0.0')`.
